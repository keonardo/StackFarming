# 🗃️ 容器 / 栈 关系系统总纲 (v1 权威版)

> 状态：**设计权威稿** | 2026-09-23
> 目的：消除「补丁式」实现——栈(Stack)与容器(Container)是**两套独立关系**，各有完整的落位/取出/生命周期。本文是所有相关代码的依据。

---

## 一、两套关系模型（核心区别）

| | **栈 Stack** | **容器 Container** |
|---|---|---|
| 适用 | 卡叠卡（鸭蛋→鸭、粽叶料合成） | 卡入地形成容器（种稻、养鱼、堆放） |
| 数据结构 | `stack_parent` / `stack_child`（单链） | 容器侧 `_slots`（格→卡）+ `_slot_owner`（卡→格） |
| 挂载标识 | `stack_parent` 指向父卡 | **内容物不可用 stack_parent 作归属**（见 §3） |
| 一父对多子 | ❌ 一父一子 | ✅ 一容器多内容物 |
| 落位 | 父卡位置 +35 偏移 | 容器内 grid 格位 |
| 生命周期 | 随父 Stack 同步 | 由容器统一管理 |
| 视觉 | 叠放（z 序 +35） | 缩略铺格 (0.55) |

> **现状 bug 根因（本文要消除的）**：内容物目前仍用 `stack_parent` 指向容器，导致每个逻辑点都要 `if terrain_parent: ... else: ...` 去猜这个 `stack_parent` 到底是不是容器。正确做法：**容器归属用专用引用 `container_parent`**，与 `stack_parent` 完全分离。

---

## 二、一张卡可能处于的三态

```
┌─────────┐   拖出/释放        ┌─────────┐    拖入               ┌─────────┐
│ 自由卡   │ ───────────────→ │ 栈子卡   │ ─────────────→     │ 容器内容物 │
│ floating│ ←───────────────  │ stacked │ ←─────────────     │ in-container│
└─────────┘   unstack/detach  └─────────┘   unstack/detach   └─────────┘
     ↑                                                   │
     └───────────────── 拖入地形 ─────────────────────────┘
              （container_parent 指向地形成）
     ↑────────────────── 拖出 / 容器销毁 ───────────────────┘
```

| 态 | 关键条件 | 引用 |
|---|---------|------|
| **自由卡** | 无父、无容器 | `stack_parent=null`, `container_parent=null` |
| **栈子卡** | stack 单链中 | `stack_parent != null` |
| **容器内容物** | 已入地形成容器 | `container_parent != null`, 且容器 `_slot_owner.has(self)` |

### 2.1 三态互斥
- 一张卡**同一时刻只能处于一态**（自由/栈/容器）
- 栈子卡**不可能同时是**容器内容物（内容物归属独立）
- 进入新态前必须**先清旧态**（见 §6 转移矩阵）

## 三、引用命名（解除 stack_parent 语义混叠）

在现有 `base_card.gd` 基础上**新增**独立字段，不再混用：

```gdscript
# 栈专用（保留，语义不变）
var stack_parent: BaseCard = null
var stack_child: BaseCard = null

# 容器专用（新增，与栈完全分离）
var container_parent: TerrainCard = null   # 我属于哪个容器
```

- **stack 链**只管栈：`stack_parent/child` 只由栈操作读写（`stack_on` 栈分支）
- **容器归属**只走 `container_parent`：进出容器时由容器写入/清空
- 所有业务查询（get_terrain、count、行为遍历）优先看 `container_parent`，再看 `stack_parent`——见 §5

## 四、落位与取出（完整流程）

### 4.1 入容器

```
拖卡 → 目标地形成容器？
  ├─ 是 → 校验 can_accept（工具/地形卡被拒）
  │       → claim_content 占格（寻最近空格）
  │       → 写 container_parent → notify_content_added
  │       → 缩略显示（scale 0.55）铺到该格
  └─ 否 → 走栈逻辑（stack_on）或其取
```

### 4.2 出容器（三种路径统一收口 `_leave_container()`）

| 触发 | 结果 |
|------|------|
| 拖出容器边界放下 | 自由卡，恢复全尺寸 |
| 容器地形被销毁/合成 | 内容物全部释放（跌落为自由/浮动卡） |
| 内容物死亡/过期 | 脱离容器后走死亡逻辑 |

```gdscript
func _leave_container() -> void:
    if container_parent == null: return
    container_parent.release_content(self)   # 释放格位
    container_parent = null                  # 清归属
    scale = Vector2.ONE                      # 恢复全尺寸
    # 不触碰 stack_parent --- 内容物本来就不在栈
```

## 五、业务查询优先级（两套关系共存时）

| 查询 | 规则 |
|------|------|
| `get_terrain()` | 优先 `container_parent`；否则栈根若是地形返回它 |
| `get_stack_chain()` | **栈链专属**：仅栈子卡（不混入容器内容物） |
| 容器遍历 | `TerrainCard._slots` 即所有内容物，行为从容器拿 |
| `count_children_of_type()` | 容器用 `_slot_owner` 统计；栈用链统计 |

> 这样行为树/计数不再依赖「猜 stack_parent 是不是容器」。

## 六、状态转移矩阵（防遗漏）

| 当前态 | 目标态 | 必经 | 涉及引用 |
|--------|--------|------|---------|
| 自由 → 栈 | `stack_on(父)` | 栈分支 | stack_parent/child |
| 自由 → 容器 | `enter_container(地形)` | §4.1 | container_parent |
| 栈 → 自由 | `unstack()` | 清栈链 | stack_parent/child |
| 容器 → 自由 | `_leave_container()` | §4.2 | container_parent, 容器 slots |
| 栈 → 容器 | 先 unstack 再 enter | 连续两次 | 全清 |
| 容器 → 栈 | 先 leave 再 stack | 连续两次 | 全清 |
| 任一 → 销毁 | 先脱离父再 queue_free | — | 两套都清 |

> **铁律**：任何 `queue_free` / 死亡 / 合成合并前，先脱离两套父关系，杜绝悬空引用。

## 七、与后续系统的接口

| 系统 | 与本模型的衔接 |
|------|---------------|
| **移动 AI / Avatar 双态(M5)** | 动物不占容器格 `_slot_owner`；只写 `container_parent` 作为栖息归属 |
| **产物浮动(M4)** | 产物生成后以「自由卡」待取；不自动入容器/栈 |
| **双手劳作(M3)** | 工具从不入容器（`can_accept` 第一拒）；劳作 = 拖工具到目标卡/内容物 |
| **合成** | 地形×地形走栈路径；工具×内容物走劳作；内容物本身不触发地形合成 |
